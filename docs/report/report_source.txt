## 1. Summary

**What the mod is.** Si_ServerPerf is a MelonLoader mod for the Silica dedicated server (1.0.17, headless). It removes main-thread work a server without a screen does not need and does some necessary work more cheaply. It consists of more than fifty separately switchable patches (**items**) in six modules. Most items are **exact**: the game reaches the same result as without the mod. Version **0.2.0 (build b21)** switches on by default the items measured to be exact and worth having, plus one change players can see: corpses and wrecks are removed after **5 s instead of 15 s**.

**Headline.** In the hardest lab test, a dense three-team fight with damage at about 522 living units (terms in section 3), the configuration closest to the 0.2.0 defaults ran at **40.1 fps** where the same server run with the mod switched off ran at 15.6 fps: 62 % less main-thread work per frame.

**Proven in the lab.** All comparisons were made inside one running server. No exception and no failed item in any configuration of any night-1 run. The new scan items matched the original code in 83 479 self-checks each, the worker-thread scans in 23 452. In a four-front layout closer to a real late-round fight the new items cut frame work by 40 to 52 % against mod off. At low unit counts the server holds its 120 fps cap anyway; there the mod gives spare time (-15 to -17 % frame work at 200 to 300 units).

**Not proven.** Nothing ran with players connected; nobody has seen the 5 s removal from a client. Real AI rounds above 320 units could not be produced on 1.0.17. Two rarely used code branches have few or no in-game self-checks (section 6). Build b21 itself was not measured; all numbers come from builds b4 to b20.

## 2. What was implemented

### 2.1 Where the work list came from

The earlier performance investigation of Silica 1.0.15 (the developer report of 3 November 2026) found that the server is limited by one thread: as units are added, the Unity main thread fills up while the other cores wait. It listed where a server frame goes at about 500 units and ranked thirteen server changes, S1 to S13, by gain per effort. Si_ServerPerf implements those recommendations as patches applied from outside, without changing the game's files. The overnight measurements added a finding the report did not have: **dead units cost about as much as living ones** for the 15 s they stay in the world, because their AI keeps scanning for targets and their bodies stay physically awake. Two of the three new default changes come from that finding.

::cap Table 2. Recommendations of the 1.0.15 report and what Si_ServerPerf 0.2.0 does with them.

### 2.2 How the mod is built

* **Items and switches.** Every item has its own on/off value in the config file and its own runtime switch. An admin (or a test script) can flip items while the server runs, through a small file the mod reads every second or through the console and chat command `perf`. Items that are off at startup are not patched at all.
* **Fail-open.** If an item throws an exception, it switches itself off for the rest of the session, logs the error once and lets the original game code run. In the measurements no item ever did this.
* **Self-checks.** The exact items that replace calculations (target scans, friendly-fire checks, registration, look-ups) can run the original code on a sample of calls and compare the answers bit for bit. The counts are in section 6.
* **Startup report.** At start the mod logs every item with its state and how many of its patch targets it found in this game build, so a game update that renames a method shows up as "absent" instead of silently doing nothing.
* **Coexistence.** All measurements ran next to Si_ServerOptimizer 0.7.1, as the community server does. The one item that would overlap with it (`LightGrid_Skip`) stays off automatically. All gains in this report come on top of Si_ServerOptimizer.

## 3. How it was measured

### 3.1 The lab and the words used

All numbers come from a lab copy of the dedicated server: Silica 1.0.17, headless, **no players connected**, frame rate capped at 120 fps, on an 8-core Ryzen 7 9800X3D. The same mods ran in every configuration: Si_AdminMod, Si_RTS_AI, Si_ServerFpsCap, Si_ServerOptimizer 0.7.1, and two lab tools, Si_PerfLab (spawns and drives the test scenarios) and Si_PerfProbe (profiler). There were two sessions: **wave 1** (16 November, builds b1 to b9) and **night 1** (16 to 17 November, builds b10 to b20).

* **Lab units**: living units spawned by the test tool. **World units** additionally count the 41 to 45 base and starter units and, in fights with damage, the dead bodies still waiting for removal.
* **Frame work**: main-thread CPU time per frame in ms, without the time spent waiting for the frame cap. Lower is better. Once the main thread is full (from about 330 lab units in the dense fight), fps = 1000 / frame work, so a 33 % cut in frame work means about +50 % fps, a 50 % cut about +100 %, a 65 % cut about +185 %.
* **Configurations** (the switch settings compared):
  * **Mod off**: the mod is loaded but every item is switched off at runtime; only the exception counter and one startup-only particle item stay on. Wave 1 showed that "loaded, all off" costs the same as no mod.
  * **Previous defaults (b10)**: the default set before 0.2.0: Headless, UpdateTiers without `Tier_IdleAgents`, the exact Targeting grid items, Services, Physics census and catch-up cap.
  * **+ new invisible items**: previous defaults + the three exact target-scan items + `DeadAgentHalt` (aim kept). This is 0.2.0 without the 5 s removal.
  * **+ 5 s wreck removal**: the above + `DeadDisposeEarly` removing every dead unit after 5 s. This is the closest measured equivalent of the **0.2.0 defaults**; it was measured once, in run b15_best_plat.
  * **+ prefiltered replay**: new invisible items + `CollectPreFiltered_Snapshot`.
  * **+ worker-thread scans (big-battle set)**: the above + `ParallelScan` + `ParallelScan_Prefiltered`. This is the opt-in set of 0.2.0, measured without the 5 s removal.
  * **Previous defaults + approximate set**: + `LosTopK`, `FriendlyFire_Cache`, `SensorPipeline_Rate` (wave 1 and early night 1 only).
  * **Parked-vehicle set**: previous defaults + `IdleForceSleep`, `AvoidanceSkipOntoResting`, `AvoidanceNoIdleDetour`, `ParkedWheelHold`.

### 3.2 Scenarios

::cap Table 4. Scenario types.
| Scenario | Layout | Damage | What it stands for |
|---|---|---|---|
| Dense three-team fight | All three teams in one 45 m circle at the map centre; dead units replaced after 2 s. Held at a target count (**plateau**: 450 or 550 targets, which actually hold ~425 or ~522 lab units) or grown by about one unit per second until fps falls below 10 (**trickle ramp**) | on | Worst case: everyone sees everyone, many deaths at once |
| Spread four-front battle | Four separate fronts; 20 % of units in the bases, 15 % in transit, 65 % at the fronts; dead units replaced | on | A hard but realistic stand-in for a big late-round fight |
| God-mode battles (wave 1) | A three-way fight at the centre plus three two-way fronts ~350 m apart, 10 % of each team patrolling, 28 structures per team | off: units target, aim and fire, nobody dies | Battle load without deaths, held at fixed counts |
| Parked vehicles | 300 AI vehicles standing still: a tight grid, four prefab grids, or spaced lots on slopes; a moving-vehicle guard and a move-order timing probe | - | Bases full of parked AI vehicles |
| Small lab scenarios (wave 1) | Idle and moving soldiers or vehicles, built structures, a mixed late-game set | - | Per-object costs below the fps cap |

How the lab relates to real rounds: the 1.0.15 AI rounds on the live server fell to 31 fps at 600 units. The no-death lab layouts follow those rounds closely (counting all living units, the four-front god-mode ramp ran 65 fps at 530 units against 65 in the rounds at 500, and 21 fps at 726 against 21 at 700), and the dense fight without deaths falls below 30 fps at 607 lab units. With damage the same dense fight falls below 30 fps at 431 to 447 lab units. So the dense fight with damage is a worst case, and a real round behaves like a battle with few deaths at a time. Lab AI rounds on 1.0.17 stopped growing at 180 to 320 units, with and without the mod, so no real round above that count was measured.

### 3.3 Switching configurations inside one running server

Each comparison ran in **one server process**. A script rewrote the mod's runtime switch file every 30 or 60 s so that the configurations took turns at the same unit count; the first 5 to 30 s after each switch were dropped. Every block of a configuration is compared with the neighbouring blocks of the reference configuration ("paired"); the **s.e.** given with a percentage is the standard error over those pairs. An effect is clear when it is well above two to three s.e.

**Why only in-run comparisons count.** Separate starts of the same scenario differ much more than many of the effects being measured, because a fight never repeats in detail (which units die where). The "new invisible items" configuration at the 550 plateau ran at 21.2, 24.6, 26.9, 27.3 and 29.5 fps in five separate starts; mod off ran at 11.9 in one start and 15.6 in another. Typical start-to-start differences are about 15 %, the worst pairs 25 to 30 %. This report therefore never compares a configuration in one run with a configuration in another run.

### 4.7 Faster removal of dead units

In the original game a dead unit stays in the world for 15 s. Clients have no timer of their own: a wreck disappears on every client at the moment the server removes it. Removing sooner is therefore the only server-side way to cut the number of bodies, and it is visible. 0.2.0 uses the fixed form: every dead unit is removed after 5 s. Night 1 also tested a form in which the removal time follows the server's fps (15 s at 45 fps and above, falling to 5 s at 25 fps and below).

### 4.8 Parked vehicles (opt-in, waiting for a client test)

### 4.9 20 Hz physics step (information only)

Running physics at 20 instead of 25 steps per second (run qc_fixed20, previous defaults with and without the item) moved the 30 fps point from 516 to 548 lab units and the 20 fps point from 577 to 620, and cut frame work by 24 to 28 % between 400 and 599 lab units (-15 % at 500 and -10 % at 800 by fit). Deaths, kills, shots and hits stayed within ±3 %. The step rate changes game logic tied to the step count (soldier ground checks, avoidance, wheel joints), so it needs a test with real players driving vehicles first.



## 5. Why big battles are slow

**Most server work is paid per second of game time, not per frame.** Physics runs 25 steps per second, every AI agent runs its behaviour tree twice per second, creature AI runs every 0.2 s, projectiles fly in game time. Call that time-driven work T' (ms per second). What is left of each second is spent on frames, each costing a roughly fixed amount F, so **fps = (1000 - T') / F**. When T' approaches 1000 ms the budget for frames collapses, and a small growth in T' halves fps. This model reproduces the measured fps of the dense fight (40, 21, 10-11 and 7 predicted against 42, 17, 10.3 and 8.3 measured).

!fig knee 160 | Figure 10. Dense fight with the mod off (run qc1): time-driven work grows only from 79 % to 88 % of each second between ~405 and ~473 lab units, but that halves the time left for frames, and fps falls from 42 to 17.

* **Dead units are the largest single cost.** In the original game a dead unit stays 15 s, its AI keeps scanning for targets, and its bodies stay awake (87 to 96 % of them). In the dense fight 18 to 19 % of world units are dead bodies, in the spread battle 24 to 27 %. Without deaths, the dense fight holds 30 fps up to 607 lab units; with deaths, up to 431 to 447.
* **Target scans are the one cost that grows faster than the unit count.** Each AI scan walks the team's whole list of detected enemies (about 400 entries in the dense fight), and in a dense fight a spatial grid cannot shorten that list because everything is in range.
* **What the mod removes.** The previous defaults mostly removed per-frame work (presentation, idle updates). The new items remove time-driven work: dead agents' AI (`DeadAgentHalt`), the cost per scanned entry (the three scan items), dead bodies (5 s removal) and, opt-in, the scans themselves from the main thread (worker-thread scans). Near saturation every saved millisecond is leveraged: at ~13 fps each 10 ms per second removed is worth about 1.8 fps.
* **What is left.** The largest remaining block is the PhysX physics step, about a third of the main thread in a big fight. No item moves it, and lowering the vehicles' physics solver iterations did not change it. Turret, creature, projectile and behaviour-tree work calls Unity objects that can only be used from the main thread, so it cannot be moved to other cores the way the target scans were.

## 8. Limits and open points

* **Lab only, no players.** Every number comes from the lab server with no client connected. `Services.Net_SkipUpdatesNoClients` acts only while no player is connected, so on a populated server that part of the saving disappears. Network cost per player was not measured.
* **Waiting for a client test:** the parked-vehicle set, the 20 Hz physics step, the worker-thread scans in a big fight, and how the 5 s removal looks to players (corpses and wrecks vanish without a fade). Hit registration on soldiers whose animators are switched off was not checked with a client either.
* **Start-to-start variance.** Separate server starts differ by about 15 % (worst cases 25 to 30 %). Only paired comparisons within one run are reported; the absolute fps of a configuration depends on the run.
* **Closest equivalent, not 0.2.0 itself.** The configuration closest to the 0.2.0 defaults (new invisible items + fixed 5 s removal) was measured once, in run b15_best_plat on build b15. The opt-in big-battle set was measured with the fps-following removal or without removal, never with the fixed 5 s. Build b21 was not measured.
* **Real rounds.** Lab AI rounds on 1.0.17 stopped growing at 180 to 320 units, with and without the mod; high counts come only from generated scenarios.
* **Not yet measured:** a `DeadAgentHalt`-only behaviour guard in a second scenario (the spread run guards the whole new set: all behaviour metrics within ±4 % at ~422 lab units); the worker-thread scans over long periods or in an AI round; the grid-pruned scan path at volume.
* **One unexplained server hang.** In a shakedown run (build b10, previous defaults, four fronts at 300 units, bases with radar stations) the fog-of-war update stalled the server for about 84 s (0.9 fps). It did not recur with all items off, with the defaults, in god mode, or in 85 minutes of ramps. The mod does not patch the stalled code, but its default `Headless.Fog_DetectedTargetLookup` runs in the method that prepares that work, so it is not ruled out. It may be related to a hang on the live server on 13 November.
